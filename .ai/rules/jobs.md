# Jobs

## Listing photos: no resolution limit, 2MB ceiling enforced server-side via ListingPhotoCompressor
Listing photo uploads accept any resolution — there is no dimension validation. Instead `ListingPhotoCompressor::compress()` is the single, authoritative guarantee that a stored photo never exceeds 2MB: it re-encodes as webp, stepping quality down and, only as a last resort, dimensions too, until the ceiling is met. Both entry points that write to the `pending-listing-photos`/`photos` collections go through it — `ListingUploadController::store()` (the direct upload) and `EnhanceListingPhoto` (the AI photo-enhancement job, which produces a PNG from OpenAI that also needs compressing). If a third upload path is ever added, route it through this service too, or the "never store more than 2MB" promise silently breaks for that path.

The client (`Form.vue`'s FilePond config) also resizes/re-encodes before upload, but that's a bandwidth optimization only, not enforcement — it can fail or be bypassed (this is literally what happened once: a 3840×2560 image reached the server unshrunk). The server-side compressor is what actually guarantees the ceiling regardless of what the client did.

`ListingPhotoCompressor` raises PHP's `memory_limit` to 512M for the duration of a compression pass (restored after) — decoding a large source image needs more than the default request memory limit, and nothing here rejects resolution upfront so it must handle genuinely huge photos. Herd's own `fpm.conf` has a commented-out `memory_limit = 512M` suggestion; this scopes the same idea to just this operation instead of a global config change.

## AI photo enhancements are capped at 5 per listing, booked on dispatch
`ListingPhotoEnhancement` is a ledger — one row per enhancement *requested*, not per candidate accepted. Discarding a candidate does not refund it, because the OpenAI call already happened. `ListingPhotoEnhancementQuota::consume()` is the only place that writes a row, and it does the count and the write inside a `Cache::lock` on the scope; the route's `throttle:5,1` still lets five requests land together, and without the lock all five read "0 used".

The scope is the listing — except the create wizard has no listing yet, so its usage books against a `draft_key` held in the session (`ListingPhotoEnhancementQuota::DRAFT_SESSION_KEY`) and `ListingController::store()` calls `claimDraft()` to re-parent those rows onto the property it just created. Two consequences to preserve: the draft key deliberately survives an abandoned wizard (it is cleared only on a successful save, so reloading the form doesn't reset the allowance), and the wizard plus the first edit share one budget of five rather than getting five each.

A *pending* upload enhanced while editing an existing listing can't name its listing from the media alone — the media belongs to the User, not the Property. `Form.vue` therefore posts `listing: props.listing?.id` on every enhance call, and `EnhanceListingPhotoRequest::listing()` resolves it. If that field goes missing the enhancement silently books to the draft allowance instead, which hands out five extra per edit; `EnhanceListingPhotoRequest` rejects a `listing` the user cannot update rather than falling back, so the gap can only ever come from the client omitting the field.

## An accepted enhancement replaces its original; `source_media_id` is the link
`EnhanceListingPhoto` stamps every candidate with `ai_enhanced` and the `source_media_id` it came from. That stamp is the only record of the pairing, and both ends of the accept flow rely on it: `Form.vue`'s `useEnhancedPhoto()` pulls the original out of the uploader, and `ListingController::withoutSupersededOriginals()` drops any submitted photo whose enhanced replacement is submitted alongside it — deleting it outright — so a client that fails to remove it can't attach both.

FilePond only fires `processfile` for files it uploaded. Photos already on the listing arrive through `:files="initialFiles"` as `type: 'local'` and fire only `addfile`, so `onPhotoAdded` is what registers their pond file id. Without it `pondFileIdByMediaId` has no entry, `removeFile()` gets handed a media id it can't resolve, and the call silently no-ops — which is how originals ended up rendered next to their enhanced copies. Any new code path that removes a photo from the pond must go through `pondFileIdByMediaId`; a media id is not a valid FilePond query.

## The queue worker's PHP is not Herd's PHP — image code must run on both
The app serves requests through Herd's PHP, but queued jobs run in the `horizon` container (`docker/horizon/Dockerfile`, `php:8.4-cli-alpine`) with only the extensions that file installs. Herd ships a broad default build, so image code can pass every manual test through the browser and still die the moment it runs in a job. This has bitten once already: `ListingPhotoCompressor::isWebp()` used `exif_imagetype()`, which Herd has and the container did not, so uploads worked and `EnhanceListingPhoto` failed 100% of the time with "Call to undefined function". The container was also missing WebP support in GD entirely (`gd --with-jpeg --with-freetype`, no `--with-webp`, no `libwebp`), which would have been the very next failure.

Before using any image or extension function in code a job can reach, check it against the container, not your shell: `docker compose exec horizon php -r 'var_dump(function_exists("…")); print_r(gd_info());'`. Prefer ext-standard functions (`getimagesize()` over `exif_imagetype()`) so the dependency doesn't exist; when an extension is genuinely required, add it to the Dockerfile and rebuild (`docker compose build horizon && docker compose up -d horizon`) — a code-only fix leaves the running worker on the old image.
